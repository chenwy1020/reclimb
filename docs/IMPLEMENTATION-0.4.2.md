# 0.4.2 实施记录

## 设计判断

模型切换的语义被限定为“下一次请求使用”。已经生成的路线和教学内容是历史版本，不能因设置变化而被后台改写；正在执行或已经预留费用的操作也必须继续使用发起时的模型。界面因此同时展示当前选择与“已有内容保持原版本”，并把模型审计放到每次调用记录中。

多个模型不是一张预设模型名单。0.4.2 保存独立配置，使学习者能按自己的服务、账户和价格填写准确模型名，并在顶部快速切换。服务商若返回实际模型名，系统将它与请求模型并列保存；若未返回，系统明确承认未知。

## 已复现故障与修正

0.4.1 的日志显示，设置改变后的请求已经使用新填写的模型名，但所有新路线都未能发布，所以屏幕仍停留在旧内容。更直接的故障是 DeepSeek 路线响应的思考 token 占据几乎全部输出额度：近期 10 次响应全部达到长度上限，累计输出中的思考部分约为 89.7%，首次响应甚至没有可见正文。

提供方适配现在根据已确认的接口能力控制思考：DeepSeek 官方结构化请求关闭思考，Fireworks 上识别的 DeepSeek Flash 长请求使用有界预算，未知服务不接收专有参数。路线正文额度提高，恢复仍限制为一次；重复章节定位从材料对象中移除，全局章节索引在 2,000 项上限内按材料均衡选取，并把纳入与省略数量明确交给模型，避免一本长材料挤掉后续材料。

路线的能力名称、先修存在性与循环、学习单元归属以及旧身份复用也进入发布前结构校验。隐式沿用身份时会沿整条先修链递归核对，避免上游能力已改变、下游单元却冒充旧身份。模型返回语法正确但关系矛盾的 JSON 时，系统会在同一操作内获得一次精炼修复机会；仍失败或生成期间目标发生变化时，相关调用明确标为已丢弃，不会长期停留在“待发布”。来源越界等严格语义校验仍直接拒绝，不能借修复放松引用边界。

## 持久化与可追溯性

旧单模型设置迁移成默认配置，不要求重新创建项目。配置元数据进入数据库和完整备份，密钥进入按配置隔离的 Windows 加密载荷且不随备份导出。每次调用保存发起时的配置、请求模型和服务商报告模型，使切换后的行为可以逐条核对。

切换模型不会撤销旧内容，也不会让旧路线冒充由新模型生成。相同道理，模型速度、价格或名称不会进入能力证据；评价是否有效仍由任务版本、帮助、争议和核验状态决定。

最终审查还收紧了几个边界：未配置密钥的配置不能成为当前模型；模型测试或切换造成的界面刷新不会覆盖尚未保存的常规设置；视觉转写单独记录为原页识别调用；凭据文件损坏或无法解密时拒绝用一项新密钥覆盖其他配置。配置元数据与密钥写入按可回滚顺序处理，密钥写入失败时不改变模型配置。恢复操作从关闭当前档案前开始阻止并发访问，并以事务日志区分准备、旧档案移走和新档案就位；状态不明确时保持阻断，等待重启恢复，而不猜测应把哪份密钥接到哪份档案。

## 验证边界

0.4.2 的自动化使用本机模拟服务，验证请求体、切换边界、费用关联、响应模型记录、迁移、备份和长度恢复，不发送私人材料或真实 AI 请求，也没有消耗此前的开发调用额度。

安装包在构建前检查所有直接运行依赖均为当前检出中的实体目录，并在解包后核对主进程所需组件与 Windows 图形二进制确实进入 `app.asar`。这项检查来自最终交付中发现并修复的一次链接式依赖漏装，随后仍须启动包内程序完成全部桌面流程。

这些修复消除了一个系统制造的阻断，并提高了模型行为的可核对性。它们没有把第三方模型变成可靠教师。路线是否真正体现“由薄读厚、再读薄”，仍要继续接受内容核验，并用真实学习中的长期推进、独立重构和迁移表现来批判。
